# Release rehearsal and production approval

Production rollout is fail-closed. The repository-owned definition is
`deployment/compose.rehearsal.yml`. Operators supply digest-pinned release,
PostgreSQL and Playwright images, a complete verified custom-format production
encrypted archive plus its file-based decryption key, and read-only secret
files. `DATABASE_URL_FILE` must address the
Compose service `db` and database `wb_rehearsal`; it is never an environment
value. `deployment/rehearse-release.sh` restores the dump into an isolated
volume, applies only checksum-tracked pending release migrations, starts API,
worker, and the independent scheduler from one image, waits for their distinct
health checks, runs browser acceptance, performs the rollback scripts, and
compares the complete affected plan rows and migration ledger.

The rehearsal generates a synthetic password and TOTP seed in a temporary,
mode-0600 directory outside the checkout. The browser reads those files and
performs the real password step and MFA step itself through a temporary HTTPS
endpoint; no authenticated cookie is injected. It proves that no session exists
before MFA, checks the Secure, HttpOnly and SameSite session cookie, follows a
safe local `returnTo` without reload, rejects
an unsafe redirect, and checks real registered API paths. This includes the
authenticated/CSRF-protected `POST /api/tenders/:id/submission` returning HTTP
423. Temporary credentials are destroyed during cleanup and never enter Git or
evidence.

The explicitly marked local WIKOS stub is only a supplemental component check.
The rehearsal itself runs the WB-Tender connector contract read-only over TLS
against `https://api.kyntrivex.com/api/health`, unless `WIKOS_HEALTH_URL` (or a
configured `WIKOS_BASE_URL`) selects another HTTPS endpoint. Success requires
HTTP 200 JSON with `status=ok`, `checks.database=up`, and `checks.redis=up`.
Evidence contains only endpoint origin/path, status, schema/body hashes and
sizes; response payload data and credentials are never logged. Production
rejects the local stub.

The successful rehearsal writes evidence tied to the exact Git commit. Production additionally requires a separate operator-owned approval file containing `APPROVE_COMMIT=<commit>`. Neither file is generated by the production script, and both must reference its current clean checkout. Production database credentials are mounted as files and are never copied to container environment metadata.

The CI job named `rehearsal-input-safety` only proves fail-closed input
validation. It is not a rehearsal and cannot emit successful rehearsal
evidence. No script changes pull-request review state. A successful local
rehearsal is not evidence of a successful GitHub Actions run and must not be
described as such.
