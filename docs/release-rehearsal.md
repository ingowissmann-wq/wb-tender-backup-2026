# Release rehearsal and production approval

Production rollout is fail-closed. The repository-owned definition is
`deployment/compose.rehearsal.yml`. Operators supply digest-pinned release,
PostgreSQL and Playwright images, an operator-owned sanitized/synthetic custom
format dump, and read-only secret files. `DATABASE_URL_FILE` must address the
Compose service `db` and database `wb_rehearsal`; it is never an environment
value. `deployment/rehearse-release.sh` restores the dump into an isolated
volume, applies only checksum-tracked pending release migrations, starts API,
worker, and scheduler from one image, waits for health, runs browser acceptance,
deliberately enters the rollback error handler, and compares the complete
affected plan rows and migration ledger.

`E2E_AUTH_FILE` is generated by the separate Admin MFA fixture and contains a
short-lived test-only `wb_session`/`wb_csrf` cookie pair, `mfaVerified: true`, a
synthetic tender ID and its submission context. It must contain no password,
TOTP seed, production cookie or production identifier. The browser checks the
real registered API paths, including authenticated/CSRF-protected
`POST /api/tenders/:id/submission` returning HTTP 423. WIKOS/Kyntrivex uses only
the explicitly marked local read-only stub in rehearsal; production rejects
that stub and fails closed when connector values are absent.

The successful rehearsal writes evidence tied to the exact Git commit. Production additionally requires a separate operator-owned approval file containing `APPROVE_COMMIT=<commit>`. Neither file is generated by the production script, and both must reference its current clean checkout. Production database credentials are mounted as files and are never copied to container environment metadata.

No script changes pull-request review state. A successful local rehearsal is not evidence of a successful GitHub Actions run and must not be described as such.
